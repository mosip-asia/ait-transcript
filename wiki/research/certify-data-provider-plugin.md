# Getting a REST-backed `DataProviderPlugin` into the Certify 0.14 `-with-plugins` image

Research note, recorded 2026-10-20. Written against `mosip/inji-certify` tag `v0.14.0` and `mosip/digital-credential-plugins` tag `v0.6.0` (both tags exist; 0.6.0 is the plugin version Certify 0.14.0 pins), read from shallow clones, plus the project's own `vc-stack/` files. Nothing was built or run. The Docker image the question names, `mosipid/inji-certify-with-plugins:0.14.0`, and the one the local Compose uses, `injistack/inji-certify-with-plugins:0.14.0`, are the same image (identical digest `sha256:eabbba9a…`, 808 MB).

## Short answer

A data-provider plugin is one Spring `@Component` that implements `io.mosip.certify.api.spi.DataProviderPlugin` (one method: `JSONObject fetchData(Map<String,Object> identityDetails)`), guarded by `@ConditionalOnProperty(value = "mosip.certify.integration.data-provider-plugin", havingValue = "<a name you choose>")`, compiled against `io.inji.certify:certify-integration-api:0.14.0` (14 KB, on Maven Central) with Java 21. Certify's jar is a Spring Boot `ZIP`-layout jar started with `-Dloader.path=/home/mosip/additional_jars/`, so any jar dropped in that directory joins the classpath; the `-with-plugins` image is just the base image with the four upstream 0.6.0 plugin jars copied there, and the upstream Compose and README document a volume mount into the same directory for custom plugins. The plugin reads its configuration with ordinary `@Value` from the mounted `certify-*.properties` (or environment overrides); no special file is needed. Certify passes the access-token JWT claims (`sub`, `scope`, `client_id`, …) as `identityDetails`, merges every top-level key of the returned `JSONObject` into the Velocity template of the matching `credential_config` row, and turns a `DataProviderExchangeException` into a `CertifyException` with the same error code. A REST example exists already: `MockIdaDataProviderPlugin`, in the same jar the image ships, autowires Certify's `RestTemplate` bean and does one `GET`. The real risks are packaging (jar-with-dependencies or no extra dependencies at all), the directory-mount hiding the bundled jars, template-contract details (`courses` must stay a pre-serialised JSON string), and an upstream HTTP call with no timeout. The whole path can be proven in the local Compose in well under a day, and the first step needs no new code.

## 1. How `digital-credential-plugins` 0.6.0 packages a data-provider plugin

The interface lives in Certify, not in the plugins repo. `certify-integration-api/src/main/java/io/mosip/certify/api/spi/DataProviderPlugin.java` (inji-certify v0.14.0) is the whole contract:

```java
public interface DataProviderPlugin {
    JSONObject fetchData(Map<String, Object> identityDetails) throws DataProviderExchangeException;
}
```

`JSONObject` is `org.json` (the parent POM pins `org.json:json:20241224`). `DataProviderExchangeException` (`certify-integration-api/.../api/exception/DataProviderExchangeException.java`) has three constructors: no-arg (code `vci_datafetch_failed`), `(String errorCode)`, and `(String errorCode, String errorMessage)`, which concatenates them as `code -> message`; `getErrorCode()` is what Certify reads back. The same module also defines `VCIssuancePlugin` (the other plugin mode, where the plugin signs the VC itself) and `VCRequestDto`; neither is needed in DataProvider mode.

Maven coordinates. The API is `io.inji.certify:certify-integration-api:0.14.0` (its POM lists only `decentralized-identity:jsonld-common-java:0.5.0` as a dependency); `certify-core:0.14.0` depends on it. Both jars and POMs are on Maven Central (`certify-integration-api-0.14.0.jar` 14,112 bytes; `certify-core-0.14.0.jar` 170,570 bytes). The upstream plugins are published under the same group: `certify-service-with-plugins/pom.xml` in inji-certify v0.14.0 pins `mock-certify-plugin`, `mosip-identity-certify-plugin`, `postgres-dataprovider-plugin` and `sunbird-rc-certify-integration-impl` all at `0.6.0` (lines 40–47) and copies them with `maven-dependency-plugin:copy`, `<type>jar</type>`, no classifier.

How the mock plugin's POM is set up (`mock-certify-plugin/pom.xml`, v0.6.0): `io.inji.certify:mock-certify-plugin:0.6.0`, packaging `jar`, compiler source/target 21; `certify-core:0.14.0`, `lombok`, `kernel-keymanager-service:1.3.0-beta.1` and `ld-signatures-java` are `provided` (they are already inside Certify); `commons-csv:1.9.0`, `esignet-core`/`esignet-integration-api:1.6.2`, `jackson-databind:2.15.4` and a few others are compile scope. The build runs `maven-assembly-plugin` 3.7.1 with `jar-with-dependencies` and `<appendAssemblyId>false</appendAssemblyId>` (line 221), so the published main artifact is the fat jar: `mock-certify-plugin-0.6.0.jar` on Maven Central is 22,588,245 bytes. That is how `commons-csv` reaches the classpath; no inji-certify POM mentions `commons-csv`. A custom plugin has to make the same choice: shade its non-provided dependencies, or use nothing Certify does not already ship.

Spring annotations. All four upstream data providers follow one pattern, for example `MockCSVDataProviderPlugin.java`:

```java
@ConditionalOnProperty(value = "mosip.certify.integration.data-provider-plugin", havingValue = "MockCSVDataProviderPlugin")
@Component
@Slf4j
public class MockCSVDataProviderPlugin implements DataProviderPlugin { ... }
```

`MockIdaDataProviderPlugin`, `PostgresDataProviderPlugin` and `IdaDataProviderPluginImpl` use the same annotation with their own simple class name as `havingValue`. The value is only a convention; Spring compares strings, so any unique name works.

How a plugin is selected. `CertifyIssuanceServiceImpl` (`certify-service/src/main/java/io/mosip/certify/services/CertifyIssuanceServiceImpl.java`, line 65) is itself `@ConditionalOnProperty(value = "mosip.certify.plugin-mode", havingValue = "DataProvider")` and has a plain `@Autowired private DataProviderPlugin dataProviderPlugin;` (line 81). So exactly one bean of that type must exist: the `@ConditionalOnProperty` on each plugin class is what guarantees that. Certify also ships one of its own, `PreAuthIssuanceServiceImpl` (`havingValue = "PreAuthDataProviderPlugin"`), under the same property. `VCIssuanceServiceImpl` is the `plugin-mode=VCIssuance` counterpart and is simply absent in DataProvider mode.

How the plugin class gets found. `CertifyServiceApplication.java` declares `@SpringBootApplication(scanBasePackages = "io.mosip.certify," + "io.mosip.kernel.crypto," + … + "${mosip.certify.integration.scan-base-package}")`. Spring resolves placeholders in each entry and then tokenises on `,; \t\n` (`ComponentScanAnnotationParser.java`, Spring Framework 6.1.4, which Spring Boot 3.2.3 uses), so the property may itself hold a comma-separated list of packages. Two consequences: first, `io.mosip.certify` is scanned unconditionally, and every upstream plugin lives under it (`io.mosip.certify.mock.integration.service`, `io.mosip.certify.postgresdataprovider…`, `io.mosip.certify.mosipid…`), so for them the `scan-base-package` property is redundant; second, a custom plugin in any other package needs the property set to that package, while one placed under `io.mosip.certify.<something>` is picked up with no property change. `resolvePlaceholders` is the lenient variant, so an unset property does not fail startup; it just scans nothing extra.

Beans the plugin can autowire from Certify. `AppConfig.java` (certify-service) defines an unconditional `RestTemplate` bean backed by Apache HttpClient 5 with a pooling connection manager (`mosip.certify.default-max-connection-per-route` / `…total-max-connection`) and cookie management disabled, and an `ObjectMapper` bean. No read or connect timeout is set on that `RestTemplate`.

## 2. How the `-with-plugins` image discovers jars and reads configuration

The base image, `certify-service/Dockerfile` (inji-certify v0.14.0): `FROM eclipse-temurin:21-jre`; `ARG loader_path=${work_dir}/additional_jars/` with `work_dir=/home/${container_user}` (so `/home/mosip/additional_jars/` for the Compose's `container_user=mosip`); `RUN mkdir -p ${loader_path}`; `ENV loader_path_env=${loader_path}`; and

```
CMD ["java", "-jar", "-Dloader.path=${loader_path_env}", "-Dspring.cloud.config.label=${spring_config_label_env}", "-Dspring.profiles.active=${active_profile_env}", "-Dspring.cloud.config.uri=${spring_config_url_env}", "certify-service.jar"]
```

`configure_start.sh` (the `ENTRYPOINT`) only unzips and installs the HSM client when `install_hsm_client=true`, then `exec "$@"`; it does nothing with jars. `certify-service/pom.xml` configures `spring-boot-maven-plugin` with `<layout>ZIP</layout>` (line 249), which selects Spring Boot's `PropertiesLauncher`. Per the Spring Boot 3.2.3 reference (executable-jar appendix, "PropertiesLauncher Features"), `loader.path` is a comma-separated classpath of directories or archives; a directory entry contributes all jar files in that directory, and earlier entries take precedence over the application's own `BOOT-INF/lib/`. So any jar in `/home/mosip/additional_jars/` is on the application classpath, including jars that shadow classes already in Certify.

The `-with-plugins` image, `certify-service-with-plugins/Dockerfile`: `FROM injistack/inji-certify:0.14.0` and `COPY ./target/*.jar ${loader_path_env}`, where `target/` holds the four 0.6.0 jars fetched by the POM above. Its README says the image "bundles runtime JARs within the Docker image, eliminating the need for an external artifact repository" and that "New plugins if needed can be mounted loader_path using a volume mount either in docker-compose or helm charts". `docs/RELEASES.md` (0.11.0, "Removal of Artifactory dependency") says the same. The upstream `docker-compose/docker-compose-injistack/docker-compose.yaml` carries the mount commented out:

```
      # This can be disabled if one uses plugins included in inji-certify-with-plugins docker image.
      #      - ./loader_path/certify/:/home/mosip/additional_jars/
```

and its README gives the recipe twice: "Recommended: Use one of the Existing Plugin" (download a 0.6.0+ jar from `https://repo1.maven.org/maven2/io/inji/certify/`, put it in `loader_path/certify/`, uncomment the mount) and "For Advanced Users: Create Custom Plugin" (implement `DataProviderPlugin` or `VCIssuancePlugin`, place the resultant JAR in `loader_path/certify/`, uncomment the mount), with `MockCSVDataProviderPlugin` named as the reference implementation.

One caveat the upstream recipe does not spell out: Docker's bind-mount documentation states that mounting onto a directory that already has files obscures the pre-existing files. Mounting a host directory over `/home/mosip/additional_jars/` therefore hides the four bundled jars for that container, so the mount must contain every jar still wanted. Mounting a single file (`./plugins/x.jar:/home/mosip/additional_jars/x.jar`) adds one jar without hiding the others; the local Compose already mounts single files into `/home/mosip/config/` this way.

Docker Hub. `mosipid/inji-certify-with-plugins:0.14.0` and `injistack/inji-certify-with-plugins:0.14.0` both exist and share digest `sha256:eabbba9a8b5a18ac8867a08afb7ece27fbd20b54d89a3ba1b2ebf9b4eeb84e53` (808,486,092 bytes, linux/amd64). `injistack/inji-certify:0.14.0` (the base, `sha256:00fe5537…`, 231 MB) exists; `mosipid/inji-certify:0.14.0` returns 404. The inji-certify `push-trigger.yml` builds both images from the `certify-service` and `certify-service-with-plugins` directories through `mosip/kattu`'s `docker-build.yml`.

Configuration. The container reads ordinary Spring Boot configuration. Both the upstream and the local Compose set `SPRING_CONFIG_NAME=certify`, `SPRING_CONFIG_LOCATION=/home/mosip/config/` and `active_profile_env=default, <usecase>`, and bind-mount `certify-default.properties` and `certify-<usecase>.properties` into that directory. Because plugin settings are plain `@Value("${…}")` injections (every upstream plugin reads its properties this way; `MockCSVDataProviderPlugin` uses `@Value` for the CSV path and columns, `MockIdaDataProviderPlugin` for its URL), they can come from any Spring property source: those files, environment variables with relaxed binding (the local Compose already overrides `mosip.certify.authn.issuer-uri` as `MOSIP_CERTIFY_AUTHN_ISSUER_URI`), or `-D` system properties. No extra mounted file is required.

The `mosip.certify.*` keys Certify itself reads in DataProvider mode (certify-service sources): `mosip.certify.plugin-mode` (`AppConfig`, `CertifyIssuanceServiceImpl`, `CredentialConfigurationServiceImpl`), `mosip.certify.integration.data-provider-plugin` (the plugin conditions and `PreAuthIssuanceServiceImpl`), `mosip.certify.integration.scan-base-package` (component scan), `mosip.certify.integration.audit-plugin` (`LoggerAuditService`, in `io.mosip.certify.plugin.impl`, so always scanned), `mosip.certify.data-provider-plugin.did-url` (issuer DID, also used by `StatusListCredentialService`), `.id-field-prefix-uri` (credential `id` prefix), `.rendering-template-id`, `.vc-expiry-duration` (default `P730D`), `.credential-status.allowed-status-purposes`, and `mosip.certify.data-provider-plugin.velocity-template.*` (`VelocityEnvConfig`, exposed to templates as `envConfigs`). `mosip.certify.integration.vci-plugin` matters only in VCIssuance mode, but `MockVCIssuancePlugin` is still instantiated when the value matches, since its class is under `io.mosip.certify`.

The `plugin_configurations` JSONB column on `certify.credential_config` (the local `certify_init.sql` fills it with the three CSV keys) maps to `CredentialConfig.pluginConfigurations` (`List<Map<String,String>>`, entity line 114) and `CredentialConfigurationDTO.pluginConfigurations`; no other code in `certify-service` or `certify-core` reads it. In 0.14.0 it is stored and returned by the credential-configuration API, not handed to the plugin. The plugin's live configuration is the properties file.

## 3. What the CSV plugin does and how the local stack uses it

`MockCSVDataProviderPlugin` (`mock-certify-plugin/src/main/java/io.mosip.certify.mock.integration/service/`, v0.6.0) reads four properties: `mosip.certify.mock.data-provider.csv-registry-uri`, `…csv.identifier-column`, `…csv.data-columns` (split on commas into a `Set<String>`) and an unused `mosip.certify.mock.vciplugin.id-uri`. Its `@PostConstruct initialize()` resolves the CSV once at startup: an `http…` URI is downloaded through the `RestTemplate` into a temp file, `classpath:` is resolved with `ResourceUtils`, anything else is a file path and a missing file throws `FileNotFoundException`, which aborts startup. It then calls `CSVReader.readCSV(file, identifierColumn, dataColumns)`.

`CSVReader` (`io.mosip.certify.util.CSVReader`, an unconditional `@Component` in the same jar) parses with `commons-csv` `CSVFormat.DEFAULT.withFirstRecordAsHeader()`, rejects a file whose header lacks the identifier column, and for each record builds a `JSONObject` with `jsonObject.put(header, record.get(header))` for every header that is in `dataColumns` or is the identifier, storing it in a `Map<String, JSONObject>` keyed by the identifier value. Mapping is therefore by header name, with `data-columns` acting as a whitelist, and every value is a `String`; the whole file is held in memory, so a changed CSV needs a Certify restart. (The repository's `CLAUDE.md` says Certify maps CSV cells to claims by position; the source says by header name. The column order in `generate_csv.py` still has to produce the right header names, but reordering would not break the mapping.)

`fetchData` reads `identityDetails.get("sub")` and returns the stored row for it; any exception becomes `DataProviderExchangeException("ERROR_FETCHING_IDENTITY_DATA")`, and a missing `sub` or row gives `DataProviderExchangeException("No Data Found")`. `sub` is the join key between the Keycloak user and the CSV `id` column.

What Certify does with the result (`CertifyIssuanceServiceImpl.getVerifiableCredential`, lines 192–316). `identityDetails` is `parsedAccessToken.getClaims()`: `AccessTokenValidationFilter` copies every claim of the decoded bearer JWT into it (lines 103–107), and the service adds `accessTokenHash` just before calling the plugin (line 193). After `fetchData` it sets `jsonObject.put("_holderId", holderId)` (251), does `templateParams.putAll(jsonObject.toMap())` (252), adds `id-field-prefix-uri + UUID` as the credential id when the prefix is set (253–254), `validFrom`/`validUntil` from now plus `vc-expiry-duration`, the `credentialStatus` block when a status purpose is configured, and the template name derived from format, type and context. `VelocityTemplatingEngineImpl.format()` looks up the `credential_config` row (`findByCredentialFormatAndCredentialTypeAndContext`, lines 115–116), base64-decodes its `vc_template`, adds `_issuer` (the `did-url`), `_dateTool` and `_esc` (Velocity `DateTool`/`EscapeTool`; there is no JSON tool), evaluates the template and parses the result as JSON (lines 219–244). A `DataProviderExchangeException` is rethrown as `CertifyException(e.getErrorCode())` (307–308); a JSON failure becomes `CertifyException(JSON_PROCESSING_ERROR, "Invalid JSON data encountered during credential generation…")` (309–311).

Local use. `vc-stack/docker-compose.yaml` runs `injistack/inji-certify-with-plugins:0.14.0` as `user: root` with `active_profile_env=default, csvdp-student`, mounts `config/certify-default.properties`, `config/certify-csvdp-student.properties`, `config/student_identity_data.csv` (git-ignored, generated from `data/students.json`) and `config/vp_request_config.json` into `/home/mosip/config/`, plus `data/CERTIFY_PKCS12` at `/home/inji/CERTIFY_PKCS12`; it has `extra_hosts: host.docker.internal:host-gateway` and no `additional_jars` mount. `config/certify-csvdp-student.properties` sets `mosip.certify.integration.scan-base-package=io.mosip.certify.mock.integration`, `audit-plugin=LoggerAuditService`, `vci-plugin=MockVCIssuancePlugin`, `mosip.certify.plugin-mode=DataProvider`, `mosip.certify.integration.data-provider-plugin=MockCSVDataProviderPlugin`, `csv.identifier-column=id`, `csv.data-columns=` the 26 columns from `id` to `thesisExamination`, `csv-registry-uri=/home/mosip/config/student_identity_data.csv`, `data-provider-plugin.did-url=did:key:…` (rewritten by `bootstrap.sh`'s `did_refresh`, lines 491–495), `id-field-prefix-uri=https://ait.example/credential/`, an empty `rendering-template-id`, the issuer display, and three `mosip.certify.indexed-mappings.*` JSONPaths (`registrationNo`, `fullName`, `academicProgram`) for ledger search. It also carries `mosip.certify.mock.authenticator.get-identity-url=http://mock-identity-system:8082/…`, which only `MockIdaDataProviderPlugin` reads and which points at a service that is not in this Compose. `smoke.sh` (line 51) reads `data-columns` from this file to check the CSV header.

`vc-stack/certify_init.sql` creates `certify.credential_config` and inserts one row, `credential_config_key_id='ait-transcript'`, format `ldp_vc`, type `AitTranscriptCredential`, context `https://www.w3.org/ns/credentials/v2` plus `http://host.docker.internal:9091/academic-transcript-context.json`, `signature_algo='EdDSA'`, `signature_crypto_suite='Ed25519Signature2020'`, `credential_status_purpose={revocation}`, a `display` block whose placeholders are `${fullName}`, `${academicProgram}`, `${degreeAwarded}`, and `plugin_configurations` echoing the three CSV keys. Its base64 `vc_template` decodes to a VCDM 2.0 document whose `credentialSubject` is `"id": "${_holderId}"` followed by one `"<claim>": "${<claim>}"` line per CSV column, with the single exception `"courses": ${courses}` (unquoted, so the CSV cell must already be valid JSON), and whose envelope uses `${_issuer}`, `${validFrom}`, `${validUntil}` and `${credentialStatus.*}`.

## 4. Existing REST or HTTP-backed data providers to copy

`MockIdaDataProviderPlugin` (`mock-certify-plugin`, v0.6.0, ~50 lines) is a genuine REST-backed `DataProviderPlugin` and it is already inside the `-with-plugins` image. It autowires Certify's `RestTemplate`, reads `mosip.certify.mock.authenticator.get-identity-url`, and in `fetchData` does `restTemplate.getForObject(getIdentityUrl + "/" + sub, HashMap.class)`, unwraps the `response` key, and copies a fixed list of fields (`fullName`, `gender`, `dateOfBirth`, `email`, `phone`, `streetAddress`→`addressLine1`, `locality`→`province`, `region`, `postalCode`, `encodedPhoto`→`face`) into a new `JSONObject` with `vcVer`, `id` and `UIN` added. Any exception becomes `DataProviderExchangeException("ERROR_FETCHING_IDENTITY_DATA")`; a missing `sub` gives `"INVALID_ACCESS_TOKEN"`. It is selectable today by changing one property value, with no new jar.

`IdaDataProviderPluginImpl` (`mosip-identity-certify-plugin`, v0.6.0) is HTTP-backed too: it loads the OIDC transaction by `accessTokenHash`, builds an `IdaKycExchangeRequest`, and `POST`s it with `restTemplate.exchange(RequestEntity.post(kycExchangeUrl/{relyingPartyId}/{clientId}).header(signature)…)`, then decrypts the returned KYC. It shows the signed-request pattern but is tied to MOSIP IDA and eSignet caches, so it is a worse template than the mock one.

`PostgresDataProviderPlugin` (`postgres-dataprovider-plugin`, v0.6.0) is SQL, not HTTP: it maps `identityDetails.get("scope")` to a query through `mosip.certify.data-provider-plugin.postgres.scope-query-mapping` and runs it with `sub` as the parameter; it is the only upstream plugin that reads `scope`, which is useful if one plugin must serve several credential types. `sunbird-rc-certify-integration-impl` implements only `VCIssuancePlugin`. Certify's own `PreAuthIssuanceServiceImpl` is a DataProvider for pre-authorised flows, not a REST client.

So the "no REST example to copy" worry is overstated: `MockIdaDataProviderPlugin` is the example, and the gap is only that it hard-codes the response shape. The AIT plugin needs two things it lacks: a pass-through from the HTTP JSON body to the `JSONObject` (keeping nested values as pre-serialised strings where the template expects them), and whatever authentication header the transcript service requires.

## 5. Concrete risks and a sub-day test plan

Risks behind "Certify plugin loading or API surprises":

- Dependencies. `PropertiesLauncher` adds only the jars present in `loader.path`; a plugin's compile-scope dependencies are not resolved at runtime. Either shade them like the mock plugin (`jar-with-dependencies`, `appendAssemblyId=false`) or depend only on what Certify ships (Spring Web's `RestTemplate`, Jackson, `org.json`, SLF4J) and mark `certify-integration-api`/`certify-core` as `provided`. A fat jar that bundles its own Spring or Jackson copies shadows Certify's (earlier `loader.path` entries win), which is the one way a plugin can break unrelated code.
- Version coupling. Compile against `certify-integration-api:0.14.0` with Java 21 (the image is `eclipse-temurin:21-jre`, the mock plugin targets 21, Certify is Spring Boot 3.2.3). Class files from a newer JDK fail to load.
- Bean selection. Exactly one `DataProviderPlugin` bean must exist. If `mosip.certify.integration.data-provider-plugin` names a value no scanned class declares, `CertifyIssuanceServiceImpl` fails to start with a missing-bean error; if two classes share the value, with a duplicate-bean error. A plugin outside `io.mosip.certify.*` also needs `mosip.certify.integration.scan-base-package` to list its package (comma-separated is fine); one under `io.mosip.certify.*` does not.
- Mount semantics. A directory mounted over `/home/mosip/additional_jars/` hides the four bundled jars; mount a single jar file instead, or accept that only the mounted jars exist.
- Template contract. `putAll(jsonObject.toMap())` means the template sees the plugin's top-level keys by name, and `_holderId`, `_issuer`, `id`, `validFrom`, `validUntil`, `credentialStatus` are reserved. `org.json` turns nested objects and arrays into `Map`/`List`, which Velocity prints as Java `toString`, not JSON, so for the current template `courses` must be returned as a JSON string, exactly as the CSV cell is today, and string values must not contain unescaped quotes. A key the template references but the plugin omits leaves a literal `${key}` in the output or breaks the JSON parse (`JSON_PROCESSING_ERROR`).
- Error and timeout surface. `DataProviderExchangeException` becomes `CertifyException(errorCode)` and the wallet sees that code; any other exception should be wrapped. Certify's `RestTemplate` bean sets pool sizes but no connect or read timeout, so a hung transcript service hangs issuance; the plugin should build its own client with timeouts or set them on a copy.
- Startup calls. The CSV plugin fails startup when its file is missing. A REST plugin must not fetch at `@PostConstruct` time, or Certify will not start when the transcript service is down.
- Networking and identity. The plugin runs inside the `certify` container, so the service must be reachable on `vc_stack_network` or via `host.docker.internal` (already in `extra_hosts`). `identityDetails` is the Keycloak token, so the service, or the plugin, must map `sub` to the student record.

Testing loading in the local Compose, in order of cost:

1. Zero-code probe (about an hour). Change `mosip.certify.integration.data-provider-plugin` in `certify-csvdp-student.properties` to `MockIdaDataProviderPlugin` and point `mosip.certify.mock.authenticator.get-identity-url` at a stub on the Compose network that answers `GET /<sub>` with `{"response": {"fullName": …}}`; recreate `certify`, run `bootstrap.sh --validate` or a wallet download. This proves the REST plugin path, the `RestTemplate` bean, container DNS and the error mapping with a jar the image already contains. The issued VC will have the wrong claims, which is fine for a loading test.
2. Skeleton plugin (two to three hours). A Maven project with `certify-integration-api:0.14.0` and `spring-web`/`org.json` as `provided`, one class, either under `io.mosip.certify.ait…` or in its own package plus `scan-base-package`, `@ConditionalOnProperty(…, havingValue = "AitRestDataProviderPlugin")`, `fetchData` doing a `GET` on `${mosip.certify.ait.data-provider.url}/{sub}` and returning `new JSONObject(body)`. Build a plain jar, add one line to the Compose `volumes:` (`./plugins/ait-rest-plugin.jar:/home/mosip/additional_jars/ait-rest-plugin.jar`), switch the property value, recreate `certify`, and read `docker compose logs certify` for a bean error or for `Data fetched successfully from Data Provider Plugin` on the first issuance.
3. Parity check (one to two hours). Serve the rows of `student_identity_data.csv` from the stub as JSON with the same 26 keys and `courses` as a string, issue one credential each way, and diff the two VCs; then run `smoke.sh`.

## What this means for the REST plugin

- Build it as `io.inji.certify`-independent Maven code compiled against `certify-integration-api:0.14.0`, Java 21, with every Certify-provided library marked `provided`; prefer no shaded dependencies at all, and if one is unavoidable, use `jar-with-dependencies` with `appendAssemblyId=false` like the mock plugin.
- Keep it to one `@Component` with `@ConditionalOnProperty` on `mosip.certify.integration.data-provider-plugin`, under `io.mosip.certify.*` if we want to leave `scan-base-package` alone; copy `MockIdaDataProviderPlugin`'s shape, but return the service's JSON as-is and keep `courses` a string.
- Give it its own HTTP client with timeouts and no startup fetch; make `DataProviderExchangeException` codes meaningful, since they surface to the wallet.
- Ship it by one single-file volume mount into `/home/mosip/additional_jars/` plus two property lines; `plugin_configurations` in `credential_config` can stay documentary.
