# Inji mobile wallet on the public deployment

Checked against `inji/inji-wallet` (main, May 2026), `inji/inji-vci-client` v0.7.0 (the native OID4VCI library the app embeds), `inji/mimoto` v0.21.0 and `inji/inji-web` v0.16.0 — the versions this stack pins.

## What the phone calls

| Step | URL the phone hits | Source of that URL |
|---|---|---|
| App start | `MIMOTO_HOST` + `/v1/mimoto/issuers`, `/allProperties`, `/verifiers` | **Baked into the app at build time** (`.env` → `react-native-dotenv`). Default points at MOSIP's `api.collab`/`api.qa-inji1`. Settings screen can edit it only if the build has `CREDENTIAL_REGISTRY_EDIT=true`. |
| Pick issuer | `<credential_issuer_host>/.well-known/openid-credential-issuer` | `credential_issuer_host` from Mimoto's issuer list |
| Discover login | `<authorization_servers[0]>/.well-known/oauth-authorization-server`, then `/openid-configuration`; takes `authorization_endpoint` | Certify's metadata |
| Login | `authorization_endpoint` in an in-app WebView; WebView intercepts any URL starting with the issuer's `redirect_uri` | Auth-server metadata; `redirect_uri` from the issuer list |
| Token | `POST <token_endpoint>` (Mimoto's `/get-token/AITUniversity`, which holds the client key) | `token_endpoint` from the issuer list |
| Credential | `credential_endpoint` from the metadata | Certify's metadata |
| After download | Verifies the VC itself; Android's native verifier fetches the VC's `@context` URLs and the status list | The VC |

So the public hostnames it needs are `api.` (Mimoto, Certify), `keycloak.` (login) — both already public, no new DNS or Caddy entries.

## Why the stack's own values break it

Mimoto and Inji Web run inside Docker and are happy with internal hostnames; a phone is not.

- Mimoto's issuer list carries `credential_issuer_host` / `wellknown_endpoint` = `http://host.docker.internal:9091`, `redirect_uri` / `token_endpoint` = `localhost:4004`. `bootstrap.sh` writes these on every run (its non-`PUBLIC_BASE_URL` branch), so they survive the template render.
- Certify's metadata has `authorization_servers: ["http://keycloak:8080/realms/inji"]`.
- **That one cannot simply be made public.** Mimoto reads the same field, then uses the auth server's `token_endpoint` (and, as the client-assertion `aud`) for its own POST. Keycloak builds back-channel endpoints from the request Host, so fetched through a public hostname it says `http://<host>:8080/...token` — unusable, and issuance in Inji Web would break.

## What was done: give the phone its own copies

Only two paths on the public gateway (`api.`) differ, and **neither is used by Inji Web, Mimoto, the demo app or Verify** (Inji Web goes `wallet.` → its own nginx → `mimoto-service`; Mimoto reads `host.docker.internal:9091`; the demo app calls `certify-nginx` directly):

| Path on `api.` | Phone gets | Everyone else |
|---|---|---|
| `GET /v1/mimoto/issuers` | static `mimoto-issuers-mobile.json`: `credential_issuer_host` = `https://api.…`, `redirect_uri` = `io.mosip.residentapp.inji://oauthredirect`, `token_endpoint` = `https://api.…/v1/mimoto/get-token/AITUniversity` | unchanged (`wallet.` path still hits Mimoto's own file) |
| `GET /.well-known/openid-credential-issuer` | Certify's metadata with `authorization_servers` rewritten to `https://keycloak.…/realms/inji` (nginx `sub_filter`) | unchanged (Mimoto fetches `certify-nginx` internally) |

Generated by [data/render_mimoto_issuers_config.py](../../data/render_mimoto_issuers_config.py) from the same template as Mimoto's file, using `CERTIFY_PUBLIC_BASE_URL`, `KEYCLOAK_PUBLIC_BASE_URL` and `INJI_WEB_URL` — all already in the VM's `app.env`, so nothing to change in `mosip-asia/ait-vc`. The gateway `include`s the generated snippet. **On a local run (`CERTIFY_PUBLIC_BASE_URL` not `https://`) the snippet is an empty comment and the gateway behaves exactly as before.**

### Why this cannot break Inji Web

- Mimoto's `mimoto-issuers-config.json` is byte-identical to before (asserted in `data/test_render_mimoto_issuers_config.py`).
- Inji Web 0.16.0 never reads `redirect_uri` or `token_endpoint` from the list: it builds `redirect_uri` from `window.location.origin + "/redirect"` (`src/utils/api.ts`).
- Mimoto uses the request's `redirect_uri` for the token call and `credential_issuer_host` only server-side (`IdpServiceImpl`, `IssuersServiceImpl`).
- A/B test: the original gateway config and the new one, both against stub upstreams, over 12 routes (`get-token`, `allProperties`, `verifiers`, `/issuers/{id}/configuration`, Certify credential, `did.json`, both context files, `/realms/`, Verify health, plus the two phone routes). Local render: all 12 byte-identical. Public render: only the two phone routes differ.

## iOS enforces RFC 8414 (issuer must equal the URL fetched)

The Inji iOS wallet's VCI library (`inji-vci-client-ios-swift` 0.7.0, `AuthorizationServerResolver`) fetches `<authorization_server>/.well-known/oauth-authorization-server` and throws `Issuer mismatch` unless its `issuer` equals that URL exactly. The Android library (Kotlin 0.7.0) does not check. Keycloak's issuer is pinned to `http://keycloak:8080/realms/inji` (Mimoto's JWT `aud` and Certify's issuer-uri need it), so on a TestFlight build the phone fetched the metadata (HTTP 200, four times in the gateway log), rejected it, and never requested the login page; the app only said the download failed.

Fix in [keycloak-nginx.conf.template](../../vc-stack/keycloak-nginx.conf.template): a `map $host` makes the `oauth-authorization-server` response carry `issuer` = `KEYCLOAK_PUBLIC_BASE_URL` for any public hostname, while a request with `Host: keycloak` (Mimoto) is byte-identical to before; `openid-configuration` is untouched. Found from the VM's gateway/Keycloak access logs (Dozzle), not from the app.

## iOS 27: UIScene lifecycle

Wallet builds with the iOS 27 SDK crash at launch (`___UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`) unless the app adopts UIScene. The wallet fork adds a `SceneDelegate` (see `ait-inji-wallet`, commit `5c740575`).

## Still open (not fixed — decisions or app-side)

1. **App build.** The phone app must be built with `MIMOTO_HOST=https://api.transcript-demo.ait-vc.dpi.ait.ac.th` (a `.env.local` and an Android/iOS build). Nothing server-side can fix this.
2. **VC `@context`** (was `http://host.docker.internal:9091/…`, which a phone cannot load; the app verifies a VC right after download and Android's native verifier fetches contexts over the network; iOS skips it for `Ed25519Signature2020`). Fixed for new credentials: `bootstrap.sh` `context_refresh()` points the credential at `https://api.…/academic-transcript-context.json` on a public deployment — see [vc-stack.md](./vc-stack.md) (JSON-LD context URL). VCs issued before that deploy keep the old URL and will still fail the phone's check; reissue them.
3. **Presenting from the phone to Verify.** `VP_SUBMISSION_SUPPORTED=false` on `verify-ui`, and Mimoto's trusted-verifiers list only has `injiverify.collab.mosip.net`. Wallet-to-Verify OpenID4VP is out of scope until that is enabled and `verify.`/`api.` entries are added.
4. **Not yet tried on a real phone.** Verified against the source of the app and libraries, not with a device.

## Check after a deploy

```sh
A=https://api.transcript-demo.ait-vc.dpi.ait.ac.th
curl -s $A/v1/mimoto/issuers | jq '.response.issuers[0] | {credential_issuer_host, redirect_uri, token_endpoint}'
curl -s $A/.well-known/openid-credential-issuer | jq .authorization_servers   # → https://keycloak.…/realms/inji
curl -s https://keycloak.transcript-demo.ait-vc.dpi.ait.ac.th/realms/inji/.well-known/oauth-authorization-server | jq .authorization_endpoint
```

Then the web wallet's normal claim (PRD §9) must still pass: that is the regression check that matters.
