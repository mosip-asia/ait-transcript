# Can the hard-copy pre-authorized flow and the REST plugin share one Certify?

Research note, recorded 2026-10-20. Written against `mosip/inji-certify` tag `v0.14.0` (commit `e54539a`, released 2026-03-25; the repository now lives at `github.com/inji/inji-certify`), read from a shallow clone, with the same repository's next release `v1.0.0-alpha.1` (2026-07-31) and its `develop` branch read over raw GitHub for the three files that decide the answer. Nothing was built or run. `digital-credential-plugins` `v0.6.0` contains nothing about pre-authorized codes. Ticket: `.scratch/issuer-v0.1/issues/12`. It builds on the plugin contract in `contracts.md` section 2a (ticket 04).

## Short answer

Not as shipped, and not in any later release: **coexistence is "only with a configuration trick that upstream does not support", otherwise no.** Two separate things make one Certify single-mode. First, the one `mosip.certify.integration.data-provider-plugin` value selects exactly one `DataProviderPlugin` bean, and upstream's pre-authorized claims source `PreAuthIssuanceServiceImpl` is one of the candidates, so with `GatewayDataProviderPlugin` selected the pre-auth cache is never read. Second, and harder, Certify's access-token filter validates every bearer token against one `mosip.certify.authn.issuer-uri` and one `mosip.certify.authn.jwk-set-uri`; pre-authorized tokens are minted and signed by Certify itself, wallet tokens by the Authorization Server, so a single Certify can accept one kind or the other. Upstream's own documentation states the consequence: configure pre-authorised issuance and "other modes—such as wallet-initiated issuance—will not be supported". The next release, `v1.0.0-alpha.1`, keeps the same annotation, the same single autowire and the same single-issuer filter; it only changes the request shape of `/pre-authorized-data`. The pre-authorized flow is otherwise complete and tested in `v0.14.0`, with one configuration bug in the shipped Compose properties. The cheapest certain alternative that keeps "the Portal obtains and redeems a pre-authorized offer, stores nothing" as written is a second, hard-copy-only Certify sharing the first one's database and key store (alternative a). A cheaper but unverified route keeps one Certify by giving both token kinds the same `iss` and serving a merged JWKS from the Gateway, with the plugin recognising pre-auth tokens (alternative e, section 4); it is a one-day experiment, not a decision. If neither is taken, the decision has to change to "the Portal obtains the credential for the hard copy through the authorization-code flow", which costs an Authorization Server customisation and a Gateway side channel (alternative b).

## 1. The pre-authorized flow in `v0.14.0`, end to end

**Creating the offer.** `PreAuthorizedCodeController` (`certify-service/src/main/java/io/mosip/certify/controller/PreAuthorizedCodeController.java`) exposes `POST /pre-authorized-data` (line 21) and `GET /credential-offer-data/{offer_id}` (line 30). The request body is `PreAuthorizedRequest` (`certify-core/src/main/java/io/mosip/certify/core/dto/PreAuthorizedRequest.java`): `credential_configuration_id` (required), `claims` (a `Map<String,Object>`, required, may be nested), `expires_in` (optional, 60 to 86400 seconds) and `tx_code` (optional, `^[A-Za-z0-9]{4,8}$`). There is no subject, no scope and no holder in the request: the caller sends the claims themselves. `PreAuthorizedCodeService.generatePreAuthorizedCode` (`certify-service/src/main/java/io/mosip/certify/services/PreAuthorizedCodeService.java`, lines 102 to 112 of the full file) validates the configuration id against the issuer metadata and, for `ldp_vc`, rejects any claim key that is not a key of the configuration's `credential_definition.credentialSubject` (`validateClaimsForLDPVC`); for `vc+sd-jwt` and `mso_mdoc` it also enforces `mandatory` claims. It then builds a `PreAuthCodeData` (configuration id, claims, `txnCode`, `createdAt`, `expiresAt`), stores it under a 32-character alphanumeric code, builds the OpenID4VCI credential offer (`credential_issuer` = `mosip.certify.identifier`, one `credential_configuration_ids` entry, `grants["urn:ietf:params:oauth:grant-type:pre-authorized_code"]` with the code and, when a `tx_code` was given, `{length, input_mode, description}`), stores the offer under a random UUID, and returns `openid-credential-offer://?credential_offer_uri=<url-encoded mosip.certify.credential-offer-url + offerId>`. The endpoint is an issuer-side management call, not a wallet call, and in both shipped property files it is on `mosip.certify.security.ignore-auth-urls` (`certify-service/src/main/resources/application-local.properties` lines 12 to 14; `docker-compose/docker-compose-injistack/config/certify-default.properties` lines 41 to 43), so it is unauthenticated by default. Upstream says so: "Client Authentication is not supported" (`docs/Pre-Authorized-Code.md` line 150).

**Where the code and the `tx_code` live.** Not in the database: in Spring caches. `VCICacheService` (`certify-service/src/main/java/io/mosip/certify/services/VCICacheService.java`) writes `PreAuthCodeData` to the `preAuthCodeCache` under `pre_auth_code:<code>` (lines 59 to 67), the offer to `credentialOfferCache` under `credential_offer:<uuid>`, and a `used:<code>` marker on redemption (`claimPreAuthCode`, line 114; `markPreAuthCodeAsUsed`, line 128, which also evicts the code). The `tx_code` is kept in clear as `txnCode` inside `PreAuthCodeData`. Expiry is the cache TTL (`mosip.certify.pre-auth.cache-expire-seconds` and `mosip.certify.credential-offer.cache-expire-seconds`, both 600 in `application-local.properties` lines 160 to 161) plus the `expiresAt` check at redemption. With `spring.cache.type=simple` (both shipped files) the caches are per-pod memory; `VCICacheService.validateCacheConfiguration` logs a "CRITICAL WARNING" about multi-pod deployments and tells you to use Redis.

**The token endpoint is Certify's own.** `OAuthController` (`certify-service/src/main/java/io/mosip/certify/controller/OAuthController.java`) serves `POST /oauth/token` (form-encoded) and, when `grant_type` is `urn:ietf:params:oauth:grant-type:pre-authorized_code` (line 119), calls `PreAuthorizedCodeService.exchangePreAuthorizedCode` (line 124); any other grant goes to `IarService.processTokenRequest`, the "presentation during issuance" authorization-code path that also lives inside Certify. Nothing is delegated to the external Authorization Server. `exchangePreAuthorizedCode` (line 320 ff.) loads the `PreAuthCodeData`, atomically claims the code (line 361), checks expiry, requires and compares `tx_code` when one was set (`tx_code_required`, `tx_code_mismatch`, lines 378 and 382), generates a `c_nonce`, and mints the access token in `generateAccessToken` (line 390 ff.): it serialises the claims map to a JSON string, reads `credential_config.scope` for the offer's configuration id (rejecting inactive or scope-less configurations), and calls (line 418) `AccessTokenJwtUtil.generateSignedJwt(claimsJson, credentialScope, "", mosip.certify.oauth.issuer, mosip.certify.oauth.access-token.audience, mosip.certify.oauth.token.expires-in-seconds, cNonce)`. `AccessTokenJwtUtil.generateSignedJwt(String identityData, …)` (`certify-service/src/main/java/io/mosip/certify/utils/AccessTokenJwtUtil.java`) builds the payload `{iss, sub = identityData, aud, iat, exp, client_id, scope, c_nonce, c_nonce_expires_in}` and signs it RS256 through the keymanager (`CERTIFY_SERVICE_APP_ID`, empty reference id). So **the pre-authorized access token's `sub` is the JSON text of the claims**, its `client_id` is the empty string, and its `scope` is the credential configuration's scope. The service then caches a `PreAuthTransaction` (configuration id, claims, `c_nonce`) in the `vcissuance` cache keyed by the token's `at_hash`, and answers `{access_token, token_type: Bearer, expires_in, c_nonce, c_nonce_expires_in}`.

**Redemption at `/issuance/credential`.** The request passes `AccessTokenValidationFilter` (`certify-service/src/main/java/io/mosip/certify/filter/AccessTokenValidationFilter.java`, `@Profile("!local")`, line 41), which decodes the JWT with `NimbusJwtDecoder.withJwkSetUri(mosip.certify.authn.jwk-set-uri)` and validates timestamps, `JwtIssuerValidator(mosip.certify.authn.issuer-uri)`, `aud` against `mosip.certify.authn.allowed-audiences`, and non-null `sub` and `client_id` (the empty string passes). On success it copies every JWT claim into the request-scoped `ParsedAccessToken.claims` and sets `accessTokenHash`. `CertifyIssuanceServiceImpl.getCredential` (`certify-service/src/main/java/io/mosip/certify/services/CertifyIssuanceServiceImpl.java`) then maps the token's `scope` (split on spaces) to a credential configuration (lines 153 to 165), fetches the `c_nonce` from the cached transaction (line 170), validates the proof JWT against `client_id` (line 172; `JwtProofValidator` lines 131 to 133 only compare `iss` with `client_id` when the proof carries an `iss`, so the Portal's proof must omit `iss`, exactly as the upstream API test `GetCredentialPreAuth.yml` does with `"client_id": ""`), adds `accessTokenHash` to the claims (line 193) and calls `dataProviderPlugin.fetchData(parsedAccessToken.getClaims())` (line 199). The holder binding comes from the proof key as in any other issuance (`_holderId`, line 251).

**What `identityDetails` contains.** For a pre-authorized redemption the map is exactly the self-minted token: `iss` = `mosip.certify.oauth.issuer`, `sub` = the claims as a JSON string, `aud` = `mosip.certify.oauth.access-token.audience`, `iat`, `exp`, `client_id` = `""`, `scope` = the configuration's `credential_config.scope`, `c_nonce`, `c_nonce_expires_in`, plus `accessTokenHash`. For an authorization-code redemption it is whatever the Authorization Server put in its access token (for Keycloak: `sub` = the user id, `scope`, `aud`, `azp`, and the `client_id` claim the filter insists on, which Keycloak only emits through a mapper). Certify sets none of these itself in that case. **The pre-auth offer does carry the claims inline**, both in the cache and, redundantly, in the token's `sub`; upstream's `PreAuthIssuanceServiceImpl` ignores `identityDetails` entirely and reads the cache, but any plugin that gets called receives the claims in `sub` anyway.

## 2. Is `PreAuthIssuanceServiceImpl` the only claims source, and is the choice exclusive?

Yes and yes, by construction. `certify-service/src/main/java/io/mosip/certify/services/PreAuthIssuanceServiceImpl.java` lines 16 to 19:

```java
@Slf4j
@Service
@ConditionalOnProperty(value = "mosip.certify.integration.data-provider-plugin", havingValue = "PreAuthDataProviderPlugin")
public class PreAuthIssuanceServiceImpl implements DataProviderPlugin {
```

Its `fetchData` (lines 27 to 51) reads `parsedAccessToken.getAccessTokenHash()`, loads the cached object (line 35), requires it to be a `PreAuthTransaction` (line 38) with non-empty claims, and returns `new JSONObject(cachedTransaction.getClaims())` (line 50). It is the only class in `certify-service` or `certify-core` that reads `PreAuthTransaction.getClaims()`. The consumer is `CertifyIssuanceServiceImpl`, lines 63 to 81:

```java
@ConditionalOnProperty(value = "mosip.certify.plugin-mode", havingValue = "DataProvider")
public class CertifyIssuanceServiceImpl implements VCIssuanceService {
    …
    @Autowired
    private DataProviderPlugin dataProviderPlugin;
```

A plain `@Autowired` of a single bean of the interface type: two candidates fail the context at startup, and the `@ConditionalOnProperty` on each implementation is what keeps the count at one. So with `mosip.certify.integration.data-provider-plugin=GatewayDataProviderPlugin`, `PreAuthIssuanceServiceImpl` is not even a bean. There is no profile, list injection, `@Primary`, or per-configuration plugin selection anywhere in `v0.14.0`; `credential_config.plugin_configurations` is stored but not consulted for selection.

What the other knobs do and do not change:

- **`mosip.certify.plugin-mode=VCIssuance`** swaps in `VCIssuanceServiceImpl`, which has no pre-auth branch at all (`certify-service/src/main/java/io/mosip/certify/services/VCIssuanceServiceImpl.java`, no reference to `PreAuth`); a pre-auth token would reach a `VCIssuancePlugin` with the claims JSON as the holder's `sub`. Not useful.
- **A delegating plugin** is possible in principle: because the claims JSON travels in the token's `sub`, a `GatewayDataProviderPlugin` that sees `client_id == ""` and a `sub` starting with `{` can parse and return it without touching Certify's caches, reproducing `PreAuthIssuanceServiceImpl` from public data. This removes the first exclusivity. It does not remove the second one, the filter.
- **The filter is the hard wall.** `AccessTokenValidationFilter` has one `issuerUri` and one `jwkSetUri`. The Compose file documents the two configurations as alternatives, with the self-issuing one commented out (`certify-default.properties` lines 220 to 224: "Use below properties to use certify as authorization server", `mosip.certify.authn.issuer-uri=${mosip.certify.authorization.url}`, `mosip.certify.authn.jwk-set-uri=…/.well-known/jwks.json`), against the live lines 64 to 65 that point at eSignet. `mosip.certify.credential-config.as-mapping` (line 256) only changes the `authorization_servers` list advertised in the issuer metadata (`CredentialConfigurationServiceImpl.resolveAuthorizationServers`, lines 345 to 349); the filter ignores it. Upstream's own words for the result, `docs/Pre-Authorized-Code.md` line 151: "If an issuer is configured to issue Verifiable Credentials using the pre-authorised flow, other modes—such as wallet-initiated issuance—will not be supported."

## 3. Is the flow complete in `v0.14.0`, and does a later release separate the two?

Complete, with rough edges. `v0.14.0` has the controller, the service with offer creation, redemption, `tx_code`, single-use and expiry checks, the DTOs, the OpenAPI entries (`docs/inji-certify-openapi.yaml` lines 1643, 1692 and 1731 for `/oauth/token`, `/pre-authorized-data` and `/credential-offer-data/{offer_id}`), unit tests (`PreAuthorizedCodeControllerTest`, `PreAuthorizedCodeServiceTest`), an API test suite (`api-test/src/main/resources/injicertify/PreAuthCodeFlow/`: generate code 11 cases, get offer 7, token exchange 7, get credential 1) and a Postman collection. The docs.inji.io release notes for 0.14.0 list "Pre-Authorized Code Flow" as a feature of this release, and the feature page repeats the single-mode limitation under "Limitations". It was not present before 0.14.0; the `v0.13.x` tags are the release before it.

Rough edges found in the source, which are configuration bugs rather than missing code: the shipped Compose properties set `mosip.certify.pre-auth-code.default-expiry-seconds`, `min-`, `max-` (lines 247 to 249) while the service reads `mosip.certify.pre-auth.default-expiry-seconds`, `min-`, `max-` (defaults 600, 60, 86400 apply instead); and the Compose `mosip.certify.cache.names` (line 174) lacks `credentialOfferCache`, which with `SimpleCacheConfig` (`certify-core/src/main/java/io/mosip/certify/core/config/SimpleCacheConfig.java`, lines 41 to 48, builds exactly the named caches) makes `VCICacheService.setCredentialOffer` throw `IllegalStateException("credentialOfferCache not available")` on the first `POST /pre-authorized-data`. `application-local.properties` line 152 has the complete list. Runnable check: start the stock Compose and post one offer; fix is one property line.

Later releases: the tag list as of 2026-10-20 is `v0.14.0` then `v1.0.0-alpha.1` (2026-07-31); there is no `v0.15.x` or `v0.16.x` tag. In `v1.0.0-alpha.1`, `PreAuthIssuanceServiceImpl` carries the identical `@ConditionalOnProperty(… havingValue = "PreAuthDataProviderPlugin")` (line 18), `CertifyIssuanceServiceImpl` still has the single `@Autowired private DataProviderPlugin dataProviderPlugin` (line 74) calling `fetchData(parsedAccessToken.getClaims())` (line 230), `AccessTokenValidationFilter` still has one `issuer-uri` and one `jwk-set-uri` with `JwtIssuerValidator(issuerUri)` (lines 44 to 75), and the Compose file keeps the same commented-out "certify as authorization server" block. The `develop` branch's `PreAuthIssuanceServiceImpl` is the same. The 1.0.0-alpha.1 release notes list one breaking change in this area, "Pre-Authorized Credential Offer API Enhancement … claims validation as per OpenID4VCI 1.0 issuer metadata", which changes the request shape, not the architecture. So no released or in-progress version separates the two providers or adds an authenticated admin API for offers.

## 4. Alternatives, costed

**(a) A second Certify instance for hard copies only.** Same image, a second deployment with `mosip.certify.integration.data-provider-plugin=PreAuthDataProviderPlugin`, `mosip.certify.authn.issuer-uri` and `jwk-set-uri` pointing at itself, `/pre-authorized-data` reachable only from the Portal (network policy, since Certify does not authenticate it), and `spring.cache.type=simple` acceptable because only this instance creates and redeems its codes and it runs as one pod. What it must share with the wallet-facing Certify: the signing key, so both issue under one DID; keys live in the keymanager tables of Certify's Postgres and are wrapped by the same keystore secret, so pointing both instances at one database with one keystore secret gives one key, and `mosip.certify.identifier`, `mosip.certify.data-provider-plugin.did-url` and `mosip.certify.domain.url` must be set to the same public values on both so the DID, `credentialStatus` URLs and `credential_issuer` are identical. Sharing the database also shares `credential_config`, the ledger (so revocation search sees hard copies) and the status lists. What may break, unverified: two instances allocating status-list indices from the same tables concurrently (`StatusListCredentialService`; pilot volume makes a collision unlikely but the check is to issue from both at once and compare `statusListIndex`), and any per-instance cache of `credential_config` going stale after the VC Lab publishes to one of them (`mosip.certify.common.cache-expire-seconds` bounds this). Cost: one more Helm release, its hostname, and the properties above; no code. Ticket 06 already discusses a second Certify.

**(b) The Portal runs the ordinary authorization-code flow as a confidential client.** The token then names the staff member, not the student, and `GatewayDataProviderPlugin` forwards only token claims; nothing in Keycloak adds a per-request `student` claim without a custom mapper or a token-exchange extension, and the authorization-code grant needs a browser login, which a server-side print job does not have. The workable shape is a Gateway side channel: the Portal tells the Gateway "the next issuance by staff S is for student X", the Gateway keys it on S's `sub`, and the plugin's ordinary `POST /issuances` resolves it. Cost: a Keycloak client plus either a mapper or the side channel, a Portal login step, and the hard-copy decision rewritten; the "stores nothing" property survives, the "pre-authorized offer" wording does not.

**(c) Upgrade to a release that separates them.** None exists (section 3). `v1.0.0-alpha.1` is an alpha and changes the `/pre-authorized-data` contract without removing the single-mode limitation.

**(d) An internal issuance API without OpenID4VCI.** There is none. The only path that produces a credential is `VCIssuanceController` (`/issuance/credential`, `/issuance/vd11/credential`, `/issuance/vd12/credential`), behind the access-token filter and the proof check; `/pre-authorized-data` only creates offers; the remaining controllers are configuration, ledger search, status, rendering template, system info and the well-known documents.

**(e) One Certify, both token kinds, by configuration (unverified).** Both exclusivities can be sidestepped without Certify code: set `mosip.certify.oauth.issuer` to the Authorization Server's issuer string so pre-auth tokens and wallet tokens share `iss`; set `mosip.certify.authn.jwk-set-uri` to a Gateway endpoint that serves the union of the Authorization Server's JWKS and Certify's own `/.well-known/jwks.json` (Nimbus selects the key by `kid`); put `mosip.certify.oauth.access-token.audience` in `allowed-audiences`; and have `GatewayDataProviderPlugin` treat a token with `client_id == ""` and a JSON `sub` as pre-authorized, returning the parsed claims. Because the Gateway would then not see the redemption, the Portal would obtain the claims from a Gateway endpoint that runs the checklist and writes the search row before it calls `/pre-authorized-data`. Cost: two property changes, one Gateway JWKS endpoint, one Gateway "prepare hard copy" endpoint, a dozen lines in the plugin, and a network rule for `/pre-authorized-data`. Risks: the merged JWKS is a contract upstream never intended, `/.well-known/oauth-authorization-server` would advertise the Authorization Server as issuer with Certify's token endpoint, and `JwtIssuerValidator` compares the exact string. Runnable check, about a day in the local Compose: mint one token each way and redeem both through the same `/issuance/credential`.

**Cheapest that keeps the decision as written:** (a), which is certain and code-free, with (e) as the cheaper experiment to run first if a second deployment is unwelcome. If neither is taken, the decision changes to (b) and "pre-authorized offer" leaves `responsibilities.md` section 5.

## What this means for the hard copy

- The Portal as OpenID4VCI client is feasible exactly as upstream intends: `POST /pre-authorized-data` with `credential_configuration_id`, the claims (keys restricted to the template's `credentialSubject`), an `expires_in`, optionally a `tx_code`; `GET /credential-offer-data/{id}`; `POST /oauth/token` with the grant and the code; `POST /issuance/credential` with a proof JWT bound to a Portal-held key, without an `iss` claim. The Portal stores nothing; Certify keeps the offer in a cache for the TTL and the credential in the ledger.
- The claims for the offer come from the Portal's caller, so the checklist must have run before the offer exists; the Gateway stays the only place that evaluates it and writes the search row. Under (a) the hard-copy Certify never calls the Gateway, so the Portal must ask the Gateway for the claims first.
- Whichever Certify serves pre-auth must (1) be the only pod, or use Redis; (2) include `credentialOfferCache` in `mosip.certify.cache.names`; (3) use the `mosip.certify.pre-auth.*` key names; (4) hide `/pre-authorized-data` behind network policy. These are property-level items for the admin-API stream and ticket 10.
- `GatewayDataProviderPlugin` should reject tokens whose `sub` is not a plain identifier only if (e) is not chosen; the contract in `contracts.md` 2a ("forward the claims map minus `accessTokenHash`") already lets the Gateway answer `no_record` for a JSON `sub`, so nothing in the plugin needs to change for (a) or (b).
- Keycloak tokens must carry a `client_id` claim for the filter, in either flow; that belongs with the Authorization Server contract, not here.
